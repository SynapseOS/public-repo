# Публичные пакеты SynapseOS

[![Build public packages](https://github.com/SynapseOS/public-repo/actions/workflows/packages.yml/badge.svg)](https://github.com/SynapseOS/public-repo/actions/workflows/packages.yml)

Рецепты сборки пакетов под SynapseOS

Сборкой управляет GNU Make. Загрузка, проверка SHA-256, применение патчей и упаковка
выполняются shell-рецептами. Собственных Python-сборщиков в дереве пакетов нет
Python нужен upstream-проектам Meson, Mako и CPython, их штатные генераторы сохранены

## Зависимости хоста

Нужен Linux x86_64, GNU Make, GCC/G++ 14, binutils, curl, jq, libarchive-tools, patch,
pkg-config, autoconf, automake, libtool, bison, flex, gperf, CMake, Ninja, Meson,
Mako, Perl, NASM, zip/unzip, JDK 21 и заголовки host libpng
Рецепты рассчитаны на Meson 1.7.2. CI устанавливает эту версию отдельно
Для сборки пакета CPython требуется host CPython 3.13, при его отсутствии рецепт
собирает его из того же закреплённого исходного архива

Пример установки системных инструментов на Debian 13:

```sh
sudo apt-get install build-essential musl-tools curl jq libarchive-tools patch pkg-config \
  autoconf automake libtool bison flex gperf cmake ninja-build meson python3-mako \
  python3-yaml python3-packaging perl nasm unzip zip libwayland-dev libpng-dev \
  libgmp-dev libmpfr-dev libmpc-dev openjdk-21-jdk-headless
```

## Сборка

```sh
make check
make all JOBS=4
make list
make netsurf JOBS=4
make -C pkgs/sqlite
```

`make` по умолчанию собирает все пакеты. `JOBS` задаёт число процессов внутри одной
сборки. Не задавайте одновременно большие значения `make -j` и `JOBS`
Пакет `musl-tools` предоставляет host-загрузчик для закреплённых инструментов LLVM
SDK собирается автоматически из `sdk/`, закрытый репозиторий и SSH-ключи не нужны
Для SDK, кэша и готовых архивов используются `.sdk`, `pkgs/.work` и `out`
Каталоги `apps`, `include` и `assets` в корне создаются как локальные ссылки на SDK

Архивы `out/<sha256>.spkg` содержат `manifest.json` и файлы `payload/` в формате USTAR
Для каждого пакета сохраняется `out/<имя>.manifest.json`
SHA-256 проверяется при каждом использовании исходного архива, включая кэш
Манифест содержит не более 512 файлов
Данные больших наборов Nmap и Open POSIX разбиты на отдельные пакеты
Чужие образы, логи и кэши не удаляются командой общей очистки

## Подпись пакетов и публикация

`make all` создаёт архивы `.spkg` и манифесты без цифровой подписи
SHA-256 исходников и файлов проверяет целостность, но не подтверждает издателя
Подпись выполняется отдельно при подготовке каталога обновлений

В формате SynapseOS ключ Ed25519 подписывает `index.json`, содержащий манифесты,
размеры и SHA-256 архивов. Отдельного файла подписи для каждого `.spkg` нет
Готовый каталог имеет структуру:

```text
current.json
snapshots/<generation>/index.json
snapshots/<generation>/index.sig
packages/<sha256>.spkg
```

`index.sig` содержит 64 байта подписи в виде 128 шестнадцатеричных символов
Для формата индекса 1 подписываются точные байты `index.json`
Для формата 2 подписывается последовательность байтов:

```text
ASCII("SynapseOS repository index v2") || 0x00 || SHA256(index.json)
```

Здесь SHA-256 представлен 32 байтами, а не строкой из 64 символов
После подписания нельзя менять даже пробелы или переводы строк индекса
Обычная подпись `ssh-keygen -Y sign` имеет другой формат и не подходит для `index.sig`

### Публикация владельцем официального каталога

В этом репозитории пока нет команды подписания или публикации
Существующая утилита выпуска `tools/setup-publish.py` находится в основном
репозитории SynapseOS и не требуется для сборки публичных пакетов
Следующий пример предназначен для сопровождающего, у которого есть эта утилита
с её файлами конфигурации, Python 3 с модулем `cryptography` и доступ к ключу владельца
Это отдельный этап выпуска, он не выполняется текущим CI

Сначала соберите пакеты и загрузите разрешённый ключ Ed25519 в SSH-agent:

```sh
make all JOBS=4
ssh-add ~/.ssh/id_ed25519
ssh-add -l
```

Перед выполнением следующего блока задайте `PUBLISH_TOOL` полным путём к утилите,
`REPO_DIR` путём к локальному каталогу публикации, `GENERATION` новым номером
поколения, а `SIGNING_PUBLIC_KEY` путём к открытому ключу в формате OpenSSH
Для `official` утилита сверяет ключ с доверенным ключом владельца и использует формат 2
Передача произвольного PEM-ключа через `--key` для `official` не разрешена

```sh
: "${PUBLISH_TOOL:?Укажите путь к tools/setup-publish.py}"
: "${REPO_DIR:?Укажите каталог публикации}"
: "${GENERATION:?Укажите новый номер поколения}"
: "${SIGNING_PUBLIC_KEY:?Укажите открытый ключ Ed25519}"

python3 "$PUBLISH_TOOL" publish \
  --repo "$REPO_DIR" \
  --id official \
  --ssh-agent-key "$SIGNING_PUBLIC_KEY" \
  --generation "$GENERATION" \
  --ttl 2592000 \
  out/*.spkg
```

Закрытый ключ остаётся в SSH-agent и не передаётся утилите
Не помещайте закрытые ключи и их пароли в Git, артефакты CI или каталог публикации
Номер поколения должен строго возрастать, `--ttl` задаётся в секундах
Изменение содержимого уже опубликованной версии требует новой версии пакета
Перед публикацией проверьте состав `out/`, пример включает все находящиеся там `.spkg`
Новая публикация должна содержать весь необходимый набор пакетов каталога

Команда готовит локальный каталог, но не загружает его на сервер
При размещении сначала передайте архивы и снимок `snapshots/<generation>/`,
а `current.json` замените последним, когда все файлы снимка уже доступны

### Проверка в SynapseOS

Доверенный открытый ключ устанавливается отдельно в `/etc/setup/keys/<имя>.pub`
В этом файле используется шестнадцатеричная запись 32 байт ключа Ed25519,
а не строка OpenSSH из файла `id_ed25519.pub`
Ключ должен соответствовать настройке каталога и быть получен по доверенному каналу

`setup update` проверяет подпись индекса, его срок действия и номер поколения
При получении пакета проверяются его размер и SHA-256 из подписанного индекса
Перед проверкой срока действия убедитесь, что в гостевой системе выставлено верное время
Успешная проверка SHA-256 отдельного архива без доверенного подписанного индекса
не подтверждает происхождение пакета

## CI и проверки

Workflow `.github/workflows/packages.yml` использует Debian 13 и выполняет `make check`, затем полную
сборку `make all JOBS=2` и сохраняет пакеты как артефакт. Он не публикует бинарники
в репозиторий обновлений и не использует секреты основного проекта
Локальная сборка и успешный CI не подтверждают работу программы в гостевой ОС
Графику, звук, сеть и пользовательский ввод нужно проверять в отдельной SynapseOS

## Исходники и лицензии

`pkgs/<имя>/` содержит манифест, закреплённые источники, патчи, Makefile и при
необходимости `recipe.sh`. Общая сборочная обвязка находится в `build/`
`sdk/` содержит исходники пользовательских библиотек, приложений и определения ABI
Реализации драйверов, локальных сокетов и фильтра ядра сюда не включены
Пользовательская утилита firewall имеет отдельную проверку конфигурации

Условия распространения определяются лицензиями соответствующих компонентов
Заголовки upstream, COPYRIGHT, COPYING и LICENSE сохранены. Единую лицензию
на все исходники репозитория этот файл не устанавливает
Поле `upstream_license` в `packages.json` отражает данные рецепта, `null` означает,
что отдельное поле лицензии в рецепте отсутствует
Данные Doom WAD не поставляются, права на них проверяются отдельно
Коммерческие зависимости исполнения не требуются для
компиляции публичных клиентских пакетов и остаются внешними пакетами

При портировании ПО использовались ИИ технологии.
Использование ИИ в коде драйверов и ядра запрещено.
